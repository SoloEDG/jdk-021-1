# 午市厨房

需要 Node.js 22 或更新版本。

```sh
npm install
npm run dev
```

类型检查及生产构建：

```sh
npm run typecheck
npm run build
```

排程沙盘引擎的独立验证（33 项规则断言，无需浏览器）：

```sh
npm run sandbox:check
```

## 排程沙盘（开餐前推演）

订单区下方的「排程沙盘」把预计订单拆成 **备料 → 占锅 → 下锅 → 起锅 → 装盘 → 交付** 五类步骤，
先在虚拟时钟上推演，再决定是否采用到实战：

- 两口煎锅由牛排与沙拉竞争，意面只能进汤锅；步骤时刻重叠会报设备冲突。
- 备料时刻与开火时刻可以拆开，但同一份食材按订单归属，不能排给两单；
  库存区实时显示「可用 / 沙盘计划消耗」，库存无法覆盖时整单标红并给出放弃原因。
- 修改任一步骤后，受影响的同订单步骤（火候、冷却）与同灶台步骤（设备冲突）会高亮，
  而不是只按截止时间重新排序。
- 目标是最大化顾客离店前的可保收入：面板汇总预计收入、可交付单数，并为每个被放弃订单
  给出 `deadline / stock / capacity / station / quality / chain` 等具体原因。
- 「自动排程」按截止时间贪心但不盲从：排不进的订单记录原因后跳过，后续订单继续尝试。
- 采用时按当前营业时刻复查库存、灶台（在灶食品不可抢占）、订单状态与容量，
  **只接纳仍可执行的连续前缀**，其余步骤留在沙盘继续调整；执行期间营业照常进行，
  若资源变化导致某步失效，执行器停下并把剩余步骤退回沙盘，不会挤掉已下锅的菜。
- 「争锅演示」构造两口煎锅之一被占用、两道菜争另一口锅的场景，可切换两种下锅顺序：
  只有先短后长（先沙拉后牛排）能同时保住两单，另一种顺序会眼睁睁看着沙拉超时。
